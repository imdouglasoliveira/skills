# Cloudflare Workers Runtime Implementation Guide

This reference explains how to build a remote MCP server on Cloudflare Workers using D1, R2, and KV, with `../templates/d1/mcp_core.sql`.

---

## 1. Handler Architecture: Stateless vs McpAgent

Cloudflare's `agents` library provides two distinct patterns:
- **`createMcpHandler`**: The preferred stateless handler for high-concurrency request/response tool execution. It creates no Durable Objects overhead and responds rapidly at the edge.
- **`McpAgent`**: Use only if your tools require continuous in-memory state or background web socket coordination between calls.

With the stateless handler, build the MCP server object **inside the request** from the already-computed effective scope, registering only the visible tools and passing `instructions` at construction. `tools/list` then can never show more than `tools/call` allows. Accept only POST; answer other methods with 405 and `Allow: POST`.

---

## 2. Integrated Authentication with `workers-oauth-provider`

For Turnkey OAuth integration in Workers:
- Configure `workers-oauth-provider` specifying `apiRoute: "/mcp"`.
- The provider populates user context and permissions into `props` forwarded directly to the MCP handler request context.
- Accept PATs on the same route through the provider's external-token hook, with the audience set to the canonical resource.
- Derive the resource metadata, the audience and the route from **one** configured URL, and normalize the trailing-slash alias before the provider sees the request.
- Never parse the provider's opaque token format to find the grant id; read it from `props` or the grant API. A library upgrade can change the format and silently break session tracking.

## 3. Relational Storage on Cloudflare D1

All relational metadata (user ceiling, OAuth clients, tokens, and audit rows) is stored in Cloudflare D1.
The database schema mirrors the Postgres table definitions; deploy it using `../templates/d1/mcp_core.sql`.

**Where OAuth state lives: two options.**

| Option | OAuth clients, requests, codes, tokens | Fits when |
|---|---|---|
| **Provider-managed** (`workers-oauth-provider`) | Kept by the library in its KV namespace. `mcp_oauth_clients`, `mcp_oauth_requests`, `mcp_oauth_codes` and `mcp_oauth_tokens` from the D1 template are not needed. | You use the library as the authorization server and accept its token format, grant API and revocation model. |
| **Own tables** (the D1 template) | In D1, hashed, with your own rotation and family revocation (`auth-modes.md`, section 6). | You run your own OAuth server on the Worker, need SQL over grants (reports, idle expiry by query, joins with the ceiling), or must stay portable to the Postgres schema. |

In both options keep in D1: `mcp_settings`, `mcp_domains`, `mcp_user_ceiling` and its history, `mcp_pats`, `mcp_request_log` and, when used, `mcp_confirmations`. With the provider option, keep a `mcp_connections`-like table only if you need "last used" or per-connection scope adjustment; revoke through the grant API (`listUserGrants`, `revokeGrant`). Do not drop the template tables you skip: leave them out of your migration.

## 4. Tenant Isolation Helpers and Testing (N-12)

Because D1 does not offer native Row Level Security policies:
- All data queries must go through an abstraction helper that refuses any query lacking explicit `tenant_id` and `user_id` parameters.
- Every project must include an automated tenant isolation test suite asserting that queries issued with one tenant context cannot read or mutate records belonging to another tenant.

Details that keep the helper honest:
- The helper injects the tenant on select, insert and update; its raw-SQL escape hatch refuses SQL without `tenant_id` and binds the tenant as the first parameter.
- State which tables are **global** by design (access lists, infrastructure) and why; give them a separate, explicit access path filtered by user, which the tenant helper refuses on purpose.
- Write a row and its audit row in **one `db.batch`**, which commits atomically.
- Keep per-user visibility inside a tenant in one module of SQL fragments, and prove with a census test that every reader goes through it (`testing.md`, section 9).

## 5. Storage Tiering: R2 and KV

- **R2 Storage**: Large binary payloads, documents, and media generated by tools must be stored in Cloudflare R2. Never embed raw file contents or base64 blobs inside tool responses; return an expiring signed URL link.
- **KV Storage**: Use Cloudflare KV for transient rate-limit counters and short-lived caching of discovery metadata.
- **Rate-limit binding**: the native `ratelimit` binding is cheaper than KV counters or counting log rows. Key it by credential (hash the key if you log it), run it after authentication and the kill switch and before any expensive step. Decide the failure policy on purpose: failing open when the binding is missing or errors is acceptable only because every call is still logged; log the call as `degraded`. The unit is the HTTP request, so a JSON-RPC batch counts once; add a per-tool cost cap if one request can fan out.

## 6. Scheduled Retention Purge

Automate log and token retention using a Cloudflare Cron Trigger defined in `wrangler.toml`. The cron handler executes an edge function that purges request logs older than the configured retention policy and cleans up expired token records.

---

## 7. Secrets and Subdomain Isolation

- Store API keys, HMAC signing keys, and external service credentials securely using `wrangler secret put`.
- Host the MCP service on an exclusive, dedicated subdomain (e.g. `mcp.example.com`) to prevent cookie leakage and cross-origin security bleed with the primary web application.
- Set `workers_dev: false` and `preview_urls: false`, so nothing reaches `/authorize` through the default hostname around an identity gateway in front of the custom domain.
- When sign-in is delegated to an identity gateway (such as Cloudflare Access), verify its JWT fully: signature, audience and issuer. A development bypass header is honored only when an explicit environment value says `dev`. Keep the gateway team domain and audience in `vars`; renaming the team changes the issuer and silently denies every sign-in.

---

## 8. Origin and Hostname Verification

Configure `allowedHostnames` and `allowedOriginHostnames` in the MCP handler options to ensure requests originate strictly from authorized client domains and approved AI interfaces.

Keep one source of truth: if your own exact Origin check runs before the handler (N-01), turn the handler's host and CORS options off or wide instead of maintaining a second, looser list. Allow exact origins only (scheme and host): known clients, loopback and the resource host. Never suffix matching, never `*.workers.dev`.

---

## 9. Platform Flags

- Enable the compatibility flag `global_fetch_strictly_public` before enabling client-metadata-document registration (CIMD): it makes outbound `fetch` public-only, which is the SSRF protection for fetching client metadata, and the OAuth library may not advertise CIMD without it. Add a test on the served authorization-server metadata that fails if CIMD support disappears.
- Lazy-load route modules with dynamic `import()` to keep cold start and CPU per invocation low.

---

## 10. Long Work and Platform Limits

Write the platform quotas that bind you (CPU per invocation, subrequests, D1 queries per invocation, cron triggers per account, queue and AI daily quotas) in the project documentation, and count loop queries against the smaller figure.
- Heavy work (OCR, bulk import, reports) is a **queue message**, not a request: the tool returns a job id and a status tool reports progress.
- Use **one cron** as a ticker that only claims due rows from a jobs table (conditional update per row, lock expiry, bounded batch, recovery of stale claims) and enqueues them. A new schedule is a row, not a new cron trigger. The cron handler ignores any expression but the expected one.
- Configure consumer retries, a dead-letter queue, and `max_batch_timeout: 0` on interactive paths. An unknown message kind is retried and then lands in the dead-letter queue.
- Queue consumers that run tools go through the same pipeline as `tools/call` (N-21).

## 11. Does not apply here

- **Supabase Edge Functions**: Gateway settings such as `verify_jwt = false` and Supabase Kong routing.
- **Supabase Auth session generation**: Using `generateLink` for a magic link or calling `verifyOtp` does not apply here; authentication in Cloudflare Workers relies on OAuth headers or PAT token checks.
- **Postgres RLS**: PostgreSQL policy statements (`create policy`) do not apply to SQLite/D1 databases.
