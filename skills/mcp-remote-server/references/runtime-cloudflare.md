# Cloudflare Workers Runtime Implementation Guide

This reference explains how to build a remote MCP server on Cloudflare Workers using D1, R2, and KV, with `../templates/d1/mcp_core.sql`.

---

## 1. Handler Architecture: Stateless vs McpAgent

Cloudflare's `agents` library provides two distinct patterns:
- **`createMcpHandler`**: The preferred stateless handler for high-concurrency request/response tool execution. It creates no Durable Objects overhead and responds rapidly at the edge.
- **`McpAgent`**: Use only if your tools require continuous in-memory state or background web socket coordination between calls.

---

## 2. Integrated Authentication with `workers-oauth-provider`

For Turnkey OAuth integration in Workers:
- Configure `workers-oauth-provider` specifying `apiRoute: "/mcp"`.
- The provider populates user context and permissions into `props` forwarded directly to the MCP handler request context.

---

## 3. Relational Storage on Cloudflare D1

All relational metadata (user ceiling, OAuth clients, tokens, and audit rows) is stored in Cloudflare D1.
The database schema mirrors the Postgres table definitions; deploy it using `../templates/d1/mcp_core.sql`.

---

## 4. Tenant Isolation Helpers and Testing (N-12)

Because D1 does not offer native Row Level Security policies:
- All data queries must go through an abstraction helper that refuses any query lacking explicit `tenant_id` and `user_id` parameters.
- Every project must include an automated tenant isolation test suite asserting that queries issued with one tenant context cannot read or mutate records belonging to another tenant.

---

## 5. Storage Tiering: R2 and KV

- **R2 Storage**: Large binary payloads, documents, and media generated by tools must be stored in Cloudflare R2. Never embed raw file contents or base64 blobs inside tool responses; return an expiring signed URL link.
- **KV Storage**: Use Cloudflare KV for transient rate-limit counters and short-lived caching of discovery metadata.

---

## 6. Scheduled Retention Purge

Automate log and token retention using a Cloudflare Cron Trigger defined in `wrangler.toml`. The cron handler executes an edge function that purges request logs older than the configured retention policy and cleans up expired token records.

---

## 7. Secrets and Subdomain Isolation

- Store API keys, HMAC signing keys, and external service credentials securely using `wrangler secret put`.
- Host the MCP service on an exclusive, dedicated subdomain (e.g. `mcp.example.com`) to prevent cookie leakage and cross-origin security bleed with the primary web application.

---

## 8. Origin and Hostname Verification

Configure `allowedHostnames` and `allowedOriginHostnames` in the MCP handler options to ensure requests originate strictly from authorized client domains and approved AI interfaces.

---

## 9. Does not apply here

- **Supabase Edge Functions**: Gateway settings such as `verify_jwt = false` and Supabase Kong routing.
- **Supabase Auth session generation**: Using `generateLink` for a magic link or calling `verifyOtp` does not apply here; authentication in Cloudflare Workers relies on OAuth headers or PAT token checks.
- **Postgres RLS**: PostgreSQL policy statements (`create policy`) do not apply to SQLite/D1 databases.
